## Code World Model

You can build a **Code World Model (CWM)**: a small program that reproduces this game's
dynamics exactly. Two payoffs. A model that matches every observation is correlated with good
understanding of the game. And a matching model is a free simulator: you can *dream* a plan in
it - roll imagined actions forward in code - instead of spending real environment steps.

You can rely on this environment being fully observable and deterministic: the same observation
and action always lead to the same next observation, and nothing relevant to the dynamics is
hidden from you. So a program that reproduces the data really can be exact.

**Automatic data collection.** Every step taken in the environment is automatically appended to
`data/transitions.jsonl`, one JSON object per line:
`{"o": <obs>, "a": <action>, "r": <reward>, "o2": <next obs>, "done": <bool>}`, where `o` and `o2`
are full observation dicts (the same shape you receive - a JSON dict holding the raw observation
plus its reward, done flag and game metadata). Do not edit this file.

You can access the data (for fixing your model) with, run from the workdir root:
```python
from world_model.verify import load_transitions
t = load_transitions()[17]     # inspect the transition of index 17
print(t.keys())                # o, a, r, o2, done  (reward/done/info also live inside o and o2)
```

**Write your model** in `world_model/` (keep all model code there):

- `model_state.py` - `State`: a class + any constants you need. Your compressed and semantic representation of one observation.
- `model_parser.py` - `parse(obs) -> State`: parse an observation into a `State` instance (a semantic representation).
- `model_render.py` - `render(state) -> obs`: rebuild the observation exactly.
- `model_transition.py` - `step(state, action) -> state`: advance the world one action, so that `render(step(parse(o), a))` is the next observation.
- `model_notes.py` - free-text notes (not scored). Use that to record your reasoning about the game.

Everything the observation contains must come back out of `render` exactly, and `step` must
predict all of it for the next observation. Keep `State` SMALL: a state as big as the observation
has understood nothing.

**Check your model on current data:** run `python world_model/verify.py` (do not edit this file).
Over your recorded data (deduplicated) it reports four staged checks - each a precondition for the
next, so it also tells you your single next priority:

1. **Parser injectivity** - do different observations parse to DIFFERENT states? If not, your
   parser is collapsing distinct observations together, i.e. dropping information the state must
   keep. Get this right first.
2. **Representation coherence** - the fraction of observations where `render(parse(o)) == o` (your
   state rebuilds the observation exactly).
3. **Transition accuracy** - the fraction of steps where `step(state, action)` reaches the real
   next state (equivalently `render(step(parse(o), a)) == o2`: grid AND reward AND done AND info).
4. **World model complexity** - the size of your code (parser/render/state/step) and of your
   states versus the observation. Smaller means more understood, less copied.

All four numbers are always shown, so you can see progress on every component; the report ends
with a verdict (valid or not) and, where the model is wrong, points at the exact
observations/transitions - by their play-order index, loadable with `load_transitions()[i]` - and
what differs, so you can study them.

**How to work.** Get representation coherence AND parser injectivity to 1.0 first - your states
are now faithful, distinct handles on each observation. THEN write `step` and drive transition
accuracy up: you are now reasoning over compact, meaningful states, not raw pixels. When several
rules fit the data, take the action that would tell them apart. When a transition refuses to fit,
suspect the representation too - the two models are one theory. Once both reach 1.0, `import
world_model` and plan by dreaming: chain `step` in code (each dreamed state already carries its
predicted reward and `is_done`) and spend real steps only to confirm.

Two habits pay off: **run verify often** - it is your fastest, cheapest feedback, so run it after
every meaningful edit, not once in a while. And **do not compress too early** - a state that drops
parts of the observation fails injectivity or coherence, and verify points at exactly the
observations it can no longer tell apart or rebuild; so start faithful, reach injectivity and
coherence 1.0, then shrink the state while keeping them there.

We advise you to adopt the following workflow:
- Fix the CWM: study the incoherent data to produce a valid CWM in `world_model/` that covers 100% of your current data.
- Use the CWM in your own debug scripts to identify interesting states that could be progress or hidden rule testing. By dreaming, plan the actions required to access a never-yet-reached state that could be interesting.
- Apply the identified strategy on the real env to actually reach that state. Then verify data with `world_model/verify.py`. You will either reach your objective and draw conclusions, or obtain incoherent transitions, which send you back to step 1.

This is only one possible workflow, the objective is that you work in a creative and scientific way to use the CWM feature to help you.
